# Design — dev-standards as Playbook for dartai + workflow

**Status:** Draft
**Date:** 2026-04-12
**Author:** brainstorm session with user
**Plugins touched:** `dev-standards`, `dartai`, `workflow`

## Context

Today, `dartai` and `workflow` both carry overlapping quality-loop and planning
content. Each embeds its own version of "what good development looks like" —
review procedures, TDD discipline, code quality standards. `dev-standards`
generates project rule files via `setup-project`, but the other two plugins
do not consume those rules at runtime.

Two external skills inspired this work:

- **Karpathy-inspired CLAUDE.md** — goal-driven execution, push back on
  assumptions, verify before claiming success, no stealth scope creep.
- **grill-me** — interview the user relentlessly about a plan until shared
  understanding is reached, walking each branch of the design tree.

The user wants both folded into the existing plugin suite, with two crucial
adjustments:

1. **Refactor-for-simplicity is preserved.** Karpathy-style rules tend to
   forbid refactoring as scope creep. We keep disciplined refactoring in the
   playbook — but only as (A) preparatory refactors planned up-front, or
   (C) discoveries surfaced in post-task review that become *new task
   proposals*. Opportunistic "while we're in here" refactors (B) remain
   forbidden.
2. **Grill questions extract both specific scope and general intent** — user
   story, user flow, design guidelines, component library, domain terms —
   so downstream decisions that would otherwise trigger mid-stream stops can
   be made with full context.

## Goals

- One playbook (`dev-standards`) defines how development happens; `dartai` and
  `workflow` consume it at runtime for scheduling and execution.
- Generic playbook adapts to project posture via `.claude/rules/` —
  a local bash script and a fintech web app should not be held to the same
  security or review thresholds.
- "Measure twice, cut once" discipline is baked in at task creation, not
  discovered mid-execution.
- Refactor backlog emerges naturally from reviews, never as silent edits.
- Duplication between `dartai/skills/code-quality.md` and
  `workflow/skills/adversarial-quality.md` collapses into a single
  dev-standards skill.

## Non-Goals

- Replacing `superpowers` skills — this sits alongside and composes with them.
- Changing how MCP servers are configured (`mcp.json.disabled` stays as-is per
  existing slop-mcp convention).
- A new task store — dartai keeps Dart, workflow keeps `.workflow/loop-state.json`.
- Enforcing opportunistic (B-class) refactoring.

## Architecture — Three Layers

```
Layer 1: Auto-loaded rules (.claude/rules/*.md)
         Thin reference pointers, always in context, <60 lines each.
         Pattern: "When X, consult dev-standards:skill-Y"
         Generated by dev-standards:setup-project.
                           |
                           | points to
                           v
Layer 2: Operational skills (plugins/dev-standards/skills/*)
         On-demand, carry the detail. Loaded only when invoked.
         Read Layer 1 rules to branch on project posture.
                           |
                           | invoked by
                           v
Layer 3: Plugin consumers (dartai, workflow)
         Add explicit invocation points at lifecycle moments.
         Never duplicate Layer 2 content.
```

**Information-flow rules:**

- Layer 1 never embeds Layer 2 content — rules are pointers, not procedures.
- Layer 2 reads Layer 1 — skills branch on project-specific thresholds.
- Layer 3 invokes Layer 2 — never inlines it.
- **Backflow:** when Layer 2 skills discover gaps in project context, they
  invoke one of two kinds of writer skills to persist enrichment:
  - **Plugin-local writers** live in `plugins/dev-standards/skills/` and are
    always available: `decide`, `update-rules`, `update-project`, `add-skill`.
  - **Project-local writers** are skill templates copied by `setup-project`
    into the target project's `.claude/skills/`:
    `write-user-story`, `define-user-flow`, `write-tech-spec` (from docs
    templates), `domain-init`, `domain-update`, `domain-check`, `domain-split`
    (from ddd templates). These are only present if the project opted into
    the matching documentation level or DDD architecture.
  - **Graceful degradation rule:** `grill-task` must probe for a project-local
    writer skill before invoking it, and if missing, fall back to recording
    the gap as a TODO line in the task spec rather than failing. Next
    iteration picks up enrichment whenever the project eventually installs
    the writer.

**Context-rot discipline:** Layer 1 is always loaded. Keeping it thin and
reference-only prevents rule files from growing into embedded procedures that
poison long sessions and loop iterations.

## dev-standards Additions

### New rule templates (`assets/templates/rules/`)

| File | Purpose | Contains | Does NOT contain |
|---|---|---|---|
| `karpathy-principles.md` | 5 named principles | goal-driven execution, push back on assumptions, surface tradeoffs, verify before success claims, no stealth scope creep; each ends with a pointer to a skill | procedures, checklists, examples, question lists |
| `refactor-discipline.md` | A/B/C rule | A (preparatory, in plan) allowed; B (opportunistic) forbidden; C (surfaced on review, becomes new task) allowed; pointers to `refactor-first-assessment` and `review-for-plan-updates` | how to refactor, which patterns to prefer |
| `grill-intake.md` | Tier gate + trigger rule | minimal tier skips, standard+ grills; two output channels (task spec + project backflow); trigger "any time a task is being created or a loop schedules work" | question bank, discovery procedure, write-back logic |

Each file targets under 60 lines. `setup-project.md` Phase 5 Step 2 copies these
alongside the existing always-loaded rules.

### New operational skills (`skills/`)

#### `grill-task/SKILL.md`

Runs at task creation. Interrogation is gated by tier (reuses the classification
from `dartai/skills/simple-planning.md`):

- **Minimal tier:** skip grill entirely, one-line spec, proceed.
- **Standard / Comprehensive / Architectural:** run layered interrogation.

**Inputs gathered before asking anything:**

- From caller: raw request, calling plugin, target task store
- From project context (silent reads): `.claude/rules/*`, `CLAUDE.md`,
  `docs/DOMAIN.md`, `docs/user-stories/`, `docs/design-guidelines.md`,
  component-library README if detected, recent related tasks
- From LCI: symbols and files matching the request's nouns/verbs

**Six question layers (ask one at a time, skip layers already covered):**

| # | Layer | Reads from | If missing, asks | Writes back via | Writer location |
|---|---|---|---|---|---|
| 1 | Intent | `docs/user-stories/` | who, outcome, measurement | `write-user-story` | project-local (docs template) |
| 2 | Flow | `docs/user-flows/` | entry, adjacent steps, exit | `define-user-flow` | project-local (docs template) |
| 3 | Domain | `docs/DOMAIN.md` | canonical terms for new concepts | `domain-update` | project-local (ddd template) |
| 4 | Design | `design-guidelines.md`, component library | pattern to follow, component to reuse | `update-rules` | **plugin-local** |
| 5 | Scope | LCI on nouns/verbs | files, not-included | task spec only | — |
| 6 | Verification | `rules/testing.md`, `rules/tdd.md` | done measurement, RED test, manual check | task spec only | — |

Project-local writers may be absent if the target project did not opt into
the matching documentation level or DDD architecture during `setup-project`.
When absent, grill-task records a `TODO` line in the task spec instead of
failing, per the graceful degradation rule above.

**Skip discipline:** if a layer's "reads from" has a confident hit, the grill
summarizes what it knows and asks "is this still accurate?" — one confirmation
rather than a fresh question. This is the mechanism that prevents grilling
into oblivion.

**Two output channels:**

- **Channel A — Task spec (ephemeral):** references to project files, not
  embedded content. Small and stable.
- **Channel B — Project context (permanent):** discovered gaps invoke writer
  skills and return a ref. Next task's grill benefits from the enrichment.

**Confirmation and termination:** before writing, proposed task spec plus
backflow writes are shown as a single confirmation screen. User approves,
edits a field, or requests another round.

**Hard caps:** max 2 follow-up rounds, max 12 questions total even for
architectural tier. Beyond that, escalate to *"task is too large, split it."*

#### `review-for-plan-updates/SKILL.md`

Runs post-GREEN, before the quality gate commits. Scope-locked — findings
never modify the just-finished task.

**Inputs:**

- `git diff <task-base>..HEAD` (only files the task touched)
- LCI call graph one hop out from changed symbols (sees who is affected)
- Project posture from `.claude/rules/karpathy-principles.md`,
  `refactor-discipline.md`, `code-quality.md` — project-specific thresholds

**Trigger catalog (C-class only):**

| Signal | Example finding |
|---|---|
| Parameter bloat | `createOrder` now has 9 params + 3 overloads → options object / builder |
| Cross-task duplication | Same validation pattern written 3× across modules |
| Naming drift | `User`, `Account`, `Customer` all used for same concept |
| Grown responsibilities | `OrderService` crossed 400 lines across last 3 tasks |
| Test setup duplication | Same fixture built inline in 5 tests |
| Visible complexity debt | Nested conditional 4-deep |
| Dead branches | Feature-flag branches for a flag on everywhere for 30+ days |

**Explicitly not looked for:** style preferences, unused imports, formatting,
anything the linter already handles.

**Output — structured plan-update proposal (YAML, not prose):**

```yaml
proposals:
  - title: "Extract OrderCreation options object"
    trigger: parameter_bloat
    evidence:
      symbol: "src/orders/create.ts:createOrder"
      observation: "9 params, 3 overloads, callers pass flags positionally"
      callers: 14   # from LCI
    rationale: "Options object removes positional confusion"
    estimated_tier: standard
    blocks: []
    urgency: low   # low | medium | high
    principle: refactor-discipline.C
```

Proposals reference evidence, never embed code.

**Routing (plugin-specific wrappers handle this):**

- `dartai`: proposals become Dart tasks in a `refactor-backlog` folder,
  tagged `origin:review` with a link back to the task that surfaced them.
- `workflow`: proposals append to `.workflow/loop-state.json` under
  `pending_plan_updates`.

**Three deferred decisions (made by planner, not reviewer):**

- **Accept now:** proposal is grilled as a normal task and scheduled next.
- **Defer:** stays in backlog with urgency tag.
- **Reject:** marked rejected with one-line reason (prevents re-proposing).

The reviewer does not decide because deciding needs full context on what else
is in flight, release cadence, and team priorities — the reviewer only sees
the diff.

#### `refactor-first-assessment/SKILL.md`

The A-rule check. Runs during planning, after `grill-task`, before steps are
written. Uses LCI to find the natural home for the change, checks whether the
existing structure supports it, and either inserts a preparatory refactor step
or signs off.

Today this logic is buried in `dartai/skills/simple-planning.md` Step 2.5 —
extracting it lets workflow reuse it.

## Collapses (Duplication Removed)

- `dartai/skills/code-quality.md` + `workflow/skills/adversarial-quality.md`
  → `dev-standards:review-for-plan-updates` + thin plugin wrappers for

- Karpathy-style principles currently scattered across planning skills
  → single `karpathy-principles.md` rule, pointers from consumers.

## Risks and Open Questions

- **Backflow write amplification.** A single grill session could invoke
  multiple writer skills, each touching project docs. Need to batch writes
  atomically so a mid-grill abort does not leave partial enrichment. Mitigation:
  grill-task collects all backflow writes into a staging object, shows them
  in the confirmation screen, writes on approval.
- **Rule-file drift from skill content.** If a skill changes its named sections
  but the rule file still references old names, pointers rot. Mitigation: rule
  files reference skill names only (e.g. `dev-standards:grill-task`), not
  sub-sections inside them.
- **Tier misclassification at creation time.** If the grill classifies a task as
  minimal and it is actually standard, the user loses the full interrogation.
  Mitigation: tier can be escalated manually during confirmation; the review
  at completion catches drift.
- **Grill fatigue on rapid task creation.** A loop firing many small tasks
  could accumulate grill prompts. Mitigation: minimal tier already skips;
  comprehensive/architectural tiers are rare in loop-driven work. Monitor.
- **Plan-update backlog unbounded growth.** If no one ever accepts proposals,
  the backlog grows. Mitigation: proposals carry urgency and age; urgency
  promotes over time; old `low` proposals auto-expire after 30 days (default,
  configurable in `.claude/rules/refactor-discipline.md`). `medium` and
  `high` proposals do not auto-expire.
- **Reject-reason memory.** Same proposal re-surfacing after rejection is
  annoying. Mitigation: reviewer writes a fingerprint (symbol + trigger
  hash) to a reject list that it checks before emitting.

## Success Criteria

- Every task created via `/dartai:task` or `/workflow:add-task` passes through
  the grill gate (minimal skips, standard+ grills), verified by invocation logs.
- `.claude/rules/` with the three new files loads at under ~150 lines total
  always-loaded context, verified by file sizes.
- `dartai/skills/code-quality.md` and `workflow/skills/adversarial-quality.md`
  shrink to thin wrappers (<80 lines each), with shared logic in
  `dev-standards:review-for-plan-updates`.
- Review proposals round-trip: a proposal emitted by review becomes a grilled
  task, verified by a single end-to-end test against a sample project.
- Backflow observed: running grill-task on a task that names a new domain
  concept results in a `DOMAIN.md` update, verified by diff.
- Context-rot check: after 20 loop iterations on a sample project, Layer 1
  rule file sizes do not grow.

## Appendix — Skills Reused as Backflow Writers

Grill-task must invoke the right skill from the right location. There are
two categories, and they live in different places.

### Plugin-local (always available)

These live in `plugins/dev-standards/skills/` and are always present when
dev-standards is installed:

| Skill | Called by grill-task when |
|---|---|
| `decide` | Grill surfaces an undecided architecture question |
| `update-rules` | Grill learns a new project-specific rule or threshold |
| `add-skill` | Grill discovers a repeatable operation that should be a project skill |
| `update-project` | Grill discovers a change to project description or conventions |

### Project-local (conditional on setup-project opts)

These are skill templates at
`plugins/dev-standards/assets/templates/skills/{docs,ddd}/` that
`setup-project` copies into the target project's `.claude/skills/`. They are
only present if the project opted into the matching documentation level or
DDD architecture:

| Skill | Template source | Present when | Called by grill-task when |
|---|---|---|---|
| `write-user-story` | `docs/` | docs level = full | Intent layer has no matching story |
| `define-user-flow` | `docs/` | docs level = full | Flow layer has no matching flow |
| `write-tech-spec` | `docs/` | docs level ≥ standard | Verification layer needs a spec doc |
| `domain-init` | `ddd/` | DDD / event-driven arch | Project has no DOMAIN.md yet |
| `domain-update` | `ddd/` | DDD / event-driven arch | Domain layer encounters a new term |
| `domain-check` | `ddd/` | DDD / event-driven arch | Domain layer needs to verify term usage |
| `domain-split` | `ddd/` | DDD / event-driven arch | Domain layer needs to split an aggregate |

**Invocation mechanism:** grill-task probes the calling project's
`.claude/skills/` directory before invoking. If the writer is absent, grill
records a `TODO: install <skill-name> to persist this gap` line in the task
spec rather than failing the session.

## Appendix — Guardrails Pulled From CLAUDE.md

From `/home/beagle/.claude/CLAUDE.md` and project `CLAUDE.md`, the spec
respects:

- Fail fast, no fallback data
- Over-engineering forbidden
- Replace and remove, do not keep old implementations as fallback
- Prefer LCI search for open-ended code exploration
