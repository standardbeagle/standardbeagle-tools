# Dev Standards Plugin Design

## Purpose

Replace bulk CLAUDE.md instructions with contextually-loaded rules and project-aware skills. A single `/setup-project` interview generates everything a project needs, then the plugin self-improves as you work.

**Core principle:** Instructions load only when relevant — language rules when editing that language, domain skills when working in that bounded context, architecture decisions always.

## What It Generates (Per-Project)

```
.claude/
├── CLAUDE.md                    # Thin — project goals, team, constraints only
├── rules/                       # Technology rules (glob-scoped)
│   ├── csharp.md               # paths: ["**/*.cs"]
│   ├── typescript.md           # paths: ["**/*.ts", "**/*.tsx"]
│   ├── testing.md              # paths: ["**/*.test.*", "**/*.spec.*"]
│   ├── data-integrity.md       # paths: ["**/db/**", "**/repositories/**"]
│   ├── version-control.md      # always loaded
│   ├── code-quality.md         # always loaded
│   └── architecture.md         # always loaded — decisions & migrations
└── skills/                      # Domain & workflow skills
    ├── add-endpoint/SKILL.md   # project-type-specific scaffolding
    ├── add-aggregate/SKILL.md  # DDD-specific if applicable
    └── ...
```

## Setup Interview (`/setup-project`)

### Phase 1: Detection (automatic)

Scans for package.json, *.csproj, go.mod, Cargo.toml, pyproject.toml, etc. Identifies frameworks (Next.js, ASP.NET, FastAPI). Finds existing test runners, linters, formatters. Checks for existing `.claude/` configuration. Detects monorepo structure.

### Phase 2: Confirm & Classify

- Confirm detected languages/frameworks
- **Project type**: script / CLI / library / desktop app (Photino) / web app / SaaS / serverless (Lambda, Cloudflare Workers)
- **Architecture style**: CRUD / DDD / event-driven / microservices / simple
- **Deployment target**: local-only / container / serverless / edge / desktop

### Phase 3: External Dependencies

- Databases, APIs, third-party services
- Which need replay proxies for testing
- Which need mocking at test boundaries

### Phase 4: Project Context

- Brief description of what's being built
- Key domain concepts (for skill generation)
- Team conventions if any

### Output

Generates all rules, skills, CLAUDE.md, and hooks in one pass. Each generated file includes a comment noting it was generated by dev-standards and can be customized.

## Rule Templates

### Always-Loaded Rules

**`version-control.md`** — Conventional commits, no debug code, no build artifacts, no secrets, split files to reduce merge conflicts, eliminate duplicates before commit.

**`code-quality.md`** — Fail fast, no dummy data, no over-engineering, tight coherent edits, check for reuse, context-aware file sizes, remove don't keep old implementations.

**`architecture.md`** — Generated from interview. Active decisions, active migrations, side effect isolation pattern, project-type-specific constraints (e.g. "this is a Cloudflare Worker — no Node.js APIs, use Web APIs only").

### Language-Scoped Rules (one per detected language)

**`typescript.md`** / **`csharp.md`** / **`python.md`** / etc. — Exception handling style, preferred patterns, avoided patterns, performance preferences, lock-free preferences, atomic writes. Customized per language idioms.

### Testing-Scoped Rules

**`testing.md`** — Fast tests, mock only at system boundaries, replay proxies for external deps, e2e tests per feature, pure functions for unit testing, no dummy data. Includes project-specific details like which test runner, which replay proxy tool, which services need replay.

### Data-Scoped Rules

**`data-integrity.md`** — Optimistic updates over transactions, idempotent saves, avoid partial writes, collect modifications and write atomically. Only generated if project has database/persistence.

## Project-Type Skill Templates

### Web App / SaaS
- `add-endpoint` — new API route following project's pattern
- `add-page` — new page/view (Next.js page, Razor page, etc.)
- `add-data-model` — new entity/table with migrations
- `add-service` — new service with side effects isolated into action objects

### DDD Projects (additional)
- `add-aggregate` — new aggregate root with invariants
- `add-domain-event` — new event with handler
- `add-value-object` — immutable value type

### CLI Tool
- `add-command` — new subcommand with args/flags
- `add-output-format` — new output formatter

### Library
- `add-public-api` — new exported function/class with docs and tests
- `add-example` — new usage example

### Desktop (Photino)
- `add-message` — new message bridge between .NET and frontend
- `add-window` — new window configuration

### Serverless
- `add-function` — new Lambda/Worker function with handler pattern
- `add-trigger` — new event trigger (HTTP, queue, schedule)

Each skill template references the architecture decisions rule so it follows current patterns.

## Self-Improvement Hooks

### Pattern Detection (PostToolUse on Write|Edit)

Lightweight hook that tracks what gets created during a session. Does not block — accumulates observations. At session end (Stop hook), if it detects repeated patterns, it suggests:

> "You added 3 new API endpoints this session, each following the same controller -> service -> repository pattern. Want me to create an add-endpoint skill for this project?"

**What it watches for:**
- Similar file structures created multiple times
- Repeated boilerplate across new files
- Consistent patterns in test setup

### Review Hook (Stop)

At session end, reviews work against current rules and architecture decisions:

- **Stale migrations**: "The Redux -> Zustand migration was marked started 2026-02-15. All files now use Zustand. Mark as complete?"
- **New conventions**: "You consistently used Result<T> for error handling in this session but there's no rule for it. Add to csharp.md?"
- **Rule conflicts**: "The testing rule says mock externals, but 3 new tests hit the live database. Update the rule or fix the tests?"

### What Hooks Don't Do

- Don't block tool execution
- Don't auto-modify rules or skills — always suggest, never act
- Don't fire on every file — batch observations, report at end
- Keep processing under 5 seconds

## Maintenance Skills

### `update-rules`
Add, modify, or remove `.claude/rules/` files. Detects current rules, shows what exists, asks what to change. Can add new glob-scoped rules for new modules/directories.

### `update-project`
Re-run parts of the setup interview. Re-detects languages/frameworks, updates CLAUDE.md project goals, adds/removes MCP servers, refreshes hook configuration.

### `add-skill`
Create new project-specific skills in `.claude/skills/`. Used when a recurring pattern emerges that should be codified.

### `decide`
Record architectural decisions and active migrations in `architecture.md`. Each entry is 1-2 lines: what's changing, from what to what, when it started. Companion `complete-migration` removes completed entries.

## Design Principles

- **Rules = technology** (how to write code) — glob-scoped, loaded by file pattern
- **Skills = domain** (what to build) — loaded by context matching
- **Always suggest, never auto-modify** — hooks propose, user approves
- **Thin CLAUDE.md** — project goals and team context only, everything else in rules/skills
- **Self-improving** — the plugin observes your work and suggests codifying patterns
